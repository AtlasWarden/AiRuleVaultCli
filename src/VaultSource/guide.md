# Rule Vault installation guide

This versioned guide is the installation provenance source. Its canonical SHA-256 is recorded as `applied_guide_sha256` in the selected vault's registry entry.

## Decision flow

1. Strictly parse the selected per-user registry and select a vault by immutable `vault_id`.
2. Compare the entry's `applied_guide_sha256` with this guide's canonical hash.
3. Verify the entry's protected-manifest anchor against `.vault-system/content-integrity.json` before trusting protected runtime files.
4. Discover legacy mandatory user content beneath bounded, non-linked `global` and `projects` trees. Existing schema-valid indexes plus valid `load_policy: always` or `integrity: protected` documents are enrolled in integrity without changing their bytes. Malformed metadata remains untrusted data for explicit archive-backed repair; it is never promoted merely because of its filename.
5. If the guide hashes match, integrity verifies, and no mandatory enrollment is needed, create an idempotent no-op plan.
6. If the guide hash differs or mandatory enrollment is needed and integrity verifies, create a reviewed update plan. Replace only an installation-owned vendor file whose current canonical hash still equals its protected-manifest entry; preserve user-owned, unknown, and ambiguous content. Use only versioned `migrations.json` rules with an exact verified vendor source for layout conversion. Archive a verified retired vendor source before removing it. A semantic three-way conflict requires review; it is never guessed from a filename, timestamp, or model output.
7. If the manifest anchor or protected-file hashes fail, preserve bytes and create a separate reviewed repair plan before updating. `restore-package` archives divergent protected bytes and restores the package runtime while retaining ordinary vault data; `accept-current` archives the prior records and records the current protected bytes as a user-approved integrity state. Missing stale manifest entries are retained in the archived prior manifest. Neither strategy bypasses verification: both rebuild or re-anchor the manifest, update the external registry anchor last, require a named integrity-repair decision, and require approval of the exact plan digest.
8. A migration to a new root copies verified source content under the same `vault_id`, verifies it, and changes the selected registry entry only as the final committed operation.

The Windows installer always presents the detected state and exact roots before it writes a plan. Applying requires approval of the plan digest. After the approved vault plan succeeds, it copies the package-verified Windows CLI to `%LOCALAPPDATA%\AI-Rule-Vault\cli\rv.exe` and writes `%LOCALAPPDATA%\AI-Rule-Vault\rule-vault-cli.json`. That descriptor is the stable, machine-readable agent entry point for `agent capabilities --format json`; an extracted install package does not need to remain available. An agent must use the opaque `agent` commands rather than requesting or inferring the private vault's filesystem location.

When an existing installation has an integrity mismatch, the interactive installer offers a short recovery choice and explains the archive location after planning. The recommended choice restores the newest package runtime while retaining existing ordinary rules, context, roles, skills, project data, and daily history. Noninteractive repair requires both `-Apply` and an explicit `-IntegrityRepairStrategy restore-package|accept-current`; there is no silent acceptance default.

After a successful interactive install, the installer can show bounded known agent bootstrap targets and, only after selection, delegates an add/update to the installed CLI. Noninteractive installation leaves agent configuration unchanged unless `-BootstrapAll` or `-BootstrapAdapter <id>` is supplied. Bootstrap discovery never creates absent agent directories, never executes agent software, and leaves ambiguous or conflicting legacy content unchanged.

Every agent registration starts a new mandatory startup contract. Before any read, write, project, daily, link, delete, or repository operation, the agent calls `agent context` with its operation, subjects, and repository-relative paths. The CLI verifies the protected route catalog, compiles the deterministic applicable packet (including root, always, dependency, current project, and matching conformance/validation routes), tracks those exact sources in a fresh opaque basis, and blocks dependent operations until this succeeds. Re-registering cannot reuse an earlier startup completion.

New private or repository Markdown classified as an index, `load_policy: always`, or `integrity: protected` is enrolled automatically in the applicable integrity manifest during the same protected transaction. In accordance with the runtime exception for daily history, daily-note content remains freshness-tracked data; daily rollover protects and re-anchors the routing/archive indexes without treating note prose as authority. Invalid repository metadata or manifests can be returned only with a data-only handling status; they never receive verified authority.

Private-vault protected content is anchored to the per-user registry. Git repository `.agents` content is deliberately different: validate its current checked-out branch with the repository ingest gate, deterministic metadata parser, current-branch manifest, and normal Git review controls. Never compare it to another developer's checkout or a private-vault manifest; those byte differences are normal branch divergence, not corruption.
